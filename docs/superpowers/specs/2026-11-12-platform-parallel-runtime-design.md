# 多平台按平台并行运行时设计

- 日期：2026-11-12
- 状态：已实现
- 技术方案：工厂函数、平台定义适配器、平台运行时注册表、全局监督器
- 当前平台：抖音、小红书

## 1. 目标

系统允许抖音和小红书各运行一个采集任务。两个平台可以同时采集，但同一平台内部保持严格串行。平台运行时、采集进程、登录状态和日志互不干扰。

本设计同时解决现有全局单例造成的耦合：

- 一个 `CollectionWorker` 只能运行一个任务。
- 一个全局 `crawler_manager` 只能承载一个采集进程。
- 一个平台登录会阻止所有平台采集。
- 一个全局日志队列会混合两个平台和不同运行的日志。
- 取消和解绑账号无法按平台隔离。

## 2. 范围

### 2.1 包含

- 使用工厂函数创建平台运行时。
- 使用 `PlatformDefinition` 集中描述平台差异和能力。
- 平台运行时注册表。
- 一个全局调度监督器和每个平台一个 Runner。
- 抖音、小红书独立采集进程和独立运行槽位。
- 按平台领取、取消、停止和恢复运行。
- 按平台隔离登录、解绑和忙状态。
- 按平台和运行 ID 隔离日志。
- 平台级运行、排队和登录状态 API。
- 管理页面展示两个平台的运行状态。
- 单元、集成、API 和前端测试。

### 2.2 不包含

- 移除全局调度器并改为每平台独立调度器。
- 多实例部署、分布式锁、数据库租约或高可用 Worker。
- 每平台独立系统服务进程。
- 同一平台多 Worker 并行。
- 新增抖音、小红书之外的可执行采集平台。
- 同一任务重复触发合并。
- 小红书端到端采集完善；该工作继续暂停。

## 3. 现有约束

- 任务表和运行表已经包含 `platform`，不需要新增字段或数据库迁移。
- 运行配置快照已经保存平台和全部任务参数。
- 每个平台使用独立的浏览器配置目录。
- 调度器仍由单个应用实例运行。
- `crawler_manager`、`collection_worker` 和日志队列当前是模块级单例。
- `login_active()` 和进程忙检查当前对所有平台生效。

## 4. 架构

### 4.1 组件关系

```text
CollectionWorkerSupervisor
  ├── Scheduler
  ├── PlatformRuntimeFactory
  └── PlatformRuntimeRegistry
        ├── PlatformRuntime(dy)
        │     ├── CrawlerManager
        │     ├── PlatformCollectionWorker
        │     └── PlatformLogBuffer
        └── PlatformRuntime(xhs)
              ├── CrawlerManager
              ├── PlatformCollectionWorker
              └── PlatformLogBuffer
```

### 4.2 PlatformDefinition

平台差异使用不可变定义和可选适配器钩子描述：

- `platform_id`：`dy` 或 `xhs`。
- `label`：中文平台名称。
- `source_modes`：支持 `search`、`detail` 中的哪些任务来源。
- `login_supported`：是否支持当前账号登录流程。
- `content_filters_supported`：是否支持排序和发布时间过滤。
- `source_parser`：校验和规范化平台来源。
- `crawler_request_factory`：把任务配置转换为上游采集器请求；平台没有特殊参数时使用通用实现。
- `comment_normalizer`：把平台原始评论映射为项目评论字段。
- `content_mapping`：内容 ID、内容链接和标题字段映射。
- `optional_hooks`：登录状态检查、运行前检查和平台特殊错误分类等可选能力。

`PlatformDefinition` 只描述平台能力和平台差异，不保存运行中状态，也不能直接启动后台任务。

平台公共代码不得继续新增 `if platform == "dy"` 或 `if platform == "xhs"` 分支。现有分支在实现时迁移到抖音和小红书各自的平台定义中。

### 4.3 工厂函数

`create_platform_runtime(definition)` 是唯一创建平台运行时的入口，负责组装：

- 一个新的 `CrawlerManager(platform_id=...)`。
- 一个新的 `PlatformCollectionWorker(platform_id, manager)`。
- 一个新的平台日志缓冲。
- 平台级忙状态和当前运行 ID。

工厂函数不直接启动后台任务。后台任务由监督器统一启动，便于测试和生命周期管理。

### 4.4 运行时注册表

`PlatformRuntimeRegistry` 在应用启动时根据已注册的 `PlatformDefinition` 创建运行时：

- 抖音运行时键为 `dy`。
- 小红书运行时键为 `xhs`。
- 未注册平台抛出明确中文异常。
- 同一平台只创建一个运行时实例。
- 注册表只提供查询，不在运行中动态替换已有运行时。

新增普通平台时，主要工作是增加平台规格、任务枚举、账号能力和上游采集器适配；调度、取消、日志和状态逻辑不复制。

### 4.4.1 新增平台接入流程

接入一个上游已有采集能力的新平台按以下步骤执行：

1. 新建平台定义模块，声明平台 ID、中文名称、支持来源、登录能力和内容筛选能力。
2. 实现来源解析和评论字段映射；上游字段与项目字段一致时可复用通用映射。
3. 仅当平台启动参数或流程不同时实现 `crawler_request_factory` 或可选钩子。
4. 将定义注册到 `PLATFORM_DEFINITIONS`，运行工厂自动创建独立运行时和 Worker。
5. 扩展任务 API 的平台枚举，使其与注册表能力一致。
6. 平台能力和状态接口自动向前端提供平台列表、中文名称和支持能力，通用下拉框无需硬编码平台 ID。
7. 增加平台 fixture、来源解析、评论映射、并行运行和日志隔离测试。

接入完成后不需要修改调度器、队列领取、取消、恢复、进程生命周期、日志缓冲或平台状态接口。

如果上游没有该平台采集器，仍必须新增采集器适配；平台定义只负责把采集器接入统一运行时，不能替代采集器本身。

### 4.5 平台采集 Worker

`PlatformCollectionWorker` 保留现有可靠队列行为：

- 只领取 `platform` 等于自身平台的任务。
- 同一平台最多一个运行处于 `running`。
- 队列按 `created_at` 先到先执行。
- 使用自己的 `CrawlerManager` 启动子进程。
- 使用自己的当前运行 ID、日志缓冲和进度计数器。
- 进程退出后完成筛选、入库和运行状态收尾。
- 一个平台失败不影响另一个平台的 Runner。

多个平台 Worker 可以同时向 PostgreSQL 写入，但每条评论和快照仍由现有唯一约束和幂等 upsert 保证一致性。

### 4.6 监督器

`CollectionWorkerSupervisor` 负责全局生命周期：

1. 启动时将所有仍为 `running` 的运行标记为 `interrupted`，并保留各自暂存目录。
2. 清理无主暂存目录。
3. 创建平台运行时。
4. 启动一个全局调度循环。
5. 为每个平台启动一个 Runner。
6. 停止时停止全部平台采集进程并取消后台任务。
7. 单个 Runner 异常时标记该平台当前运行失败，其他 Runner 继续工作。

调度仍每 5 秒扫描到期任务，不改定时计算规则。

### 4.7 运行领取

平台 Worker 的领取查询必须同时满足：

- `CollectionRun.status == "queued"`。
- 关联任务的 `platform` 等于 Worker 平台。
- 该平台当前没有登录或已启动的采集进程。
- 使用 `FOR UPDATE SKIP LOCKED` 避免并发领取同一运行。

领取后立即将运行状态改为 `running` 并初始化阶段和进度。

任务在排队后变为停用状态时，相应运行按现有规则取消。

## 5. 生命周期

### 5.1 启动

应用启动顺序：

1. 执行数据库迁移。
2. 恢复中断运行。
3. 创建平台运行时。
4. 启动调度器和平台 Runner。

### 5.2 停止

应用关闭顺序：

1. 停止全部平台采集进程。
2. 取消调度器和全部平台 Runner。
3. 等待后台任务退出。
4. 关闭数据库连接。

### 5.3 单平台失败

- 采集器启动失败：只将当前平台当前运行标记为 `failed`，平台 Runner 等待下一次领取。
- 进程异常退出：保留已暂存数据，按现有部分成功规则入库。
- Runner 未捕获异常：监督器记录平台和异常类型，只重启该平台 Runner。
- 另一平台的进程、运行和日志不受影响。

## 6. 登录与账号状态

账号服务通过注册表获取指定平台运行时：

- 抖音登录只占用抖音槽位。
- 小红书登录只占用小红书槽位。
- 抖音采集时允许小红书登录，反之亦然。
- 同一平台已有采集或登录进程时拒绝再次启动登录。
- 同一平台采集或登录进行中时拒绝解绑该平台账号。
- 其他平台运行期间允许解绑当前空闲平台账号。

所有忙状态提示使用中文，并明确平台名称。

## 7. 取消

`request_cancel(run_id)` 由监督器执行：

1. 在平台运行时中查找当前运行 ID。
2. 只停止匹配运行时对应平台的采集进程。
3. 其他平台继续运行。
4. 排队中的运行仍由 API 直接标记为取消，不启动进程。
5. 已结束运行返回现有中文冲突提示。

## 8. 日志与状态

### 8.1 日志

每个 `CrawlerManager` 拥有独立日志缓冲和队列。日志条目增加：

- `platform`：`dy` 或 `xhs`。
- `run_id`：任务采集运行 ID；登录进程可以为空。

每个平台保留最近 500 条跨运行日志，启动下一轮时不丢弃已完成运行的日志。运行详情日志接口支持 `platform` 和 `run_id` 参数，只返回匹配记录。没有匹配参数时，兼容接口返回按时间合并的平台日志。

WebSocket 日志消息包含平台字段；客户端可按该字段过滤。旧客户端收到额外字段时保持兼容。

### 8.2 平台状态

新增受管理员认证保护的平台状态接口，返回：

- 平台 ID 和中文名称。
- 支持的来源模式、登录能力和内容筛选能力。
- `process_status`：`idle`、`running`、`stopping` 或 `error`。
- 当前运行 ID。
- 当前运行任务 ID。
- 当前运行开始时间。
- `queued_count`。
- `login_state`。
- 最近活动时间。
- 最近错误的中文安全摘要。

管理页面在任务统计区展示两个平台状态卡片，并根据运行列表计算或刷新平台运行数和排队数。所有展示文本为中文。

## 9. API 兼容

- `/crawler/start` 根据请求中的 `platform` 选择运行时。
- `/crawler/stop` 支持可选 `platform`；提供平台时只停止该平台，未提供时停止全部平台以保持旧行为。
- `/crawler/status` 未提供平台时返回聚合状态，并提供各平台状态；提供平台时返回该平台状态。
- `/crawler/logs` 支持 `platform`、`run_id` 和 `limit`。
- 新增平台状态接口供管理页面使用。
- 任务创建、运行、取消和筛选 API 路径保持不变。

## 10. 数据库与一致性

- 不新增数据库列或迁移。
- 平台从关联任务读取，不从运行 ID 前缀猜测。
- 两个平台可以在不同数据库事务中同时写入。
- 评论主记录和运行快照继续使用现有唯一键。
- 运行状态更新按运行 ID 定位，不使用全局单一 ID。
- 调度器创建任务运行与现有事务规则保持一致。

## 11. 测试策略

### 11.1 单元测试

- 工厂为抖音和小红书创建不同 `CrawlerManager`。
- 同一平台重复获取返回同一运行时。
- 未注册平台返回中文错误。
- 测试中注册一个假平台定义即可创建通用 Worker，不需要修改 Worker 主流程。
- 重复注册平台 ID 被拒绝。
- 平台能力查询与实际注册表一致。
- 来源解析和评论字段映射通过平台定义调用，不在公共代码中写平台分支。
- 运行时拥有独立日志缓冲和登录状态。
- 平台 Worker 只领取本平台运行。
- 同一平台第二个运行保持排队。
- 两个平台可以同时领取和运行。
- 取消抖音运行不停止小红书进程。
- 抖音登录不阻止小红书领取任务。
- 一个 Runner 异常后另一个继续工作。

### 11.2 集成测试

- 两种平台各创建一条运行，监督器启动后两条同时进入 `running`。
- 同一平台创建两条运行，第二条在第一条结束前保持 `queued`。
- 两个平台运行的日志包含正确平台和运行 ID，不交叉返回。
- 服务启动时将两个平台的运行分别标记为 `interrupted`。
- 应用停止时两个采集进程均被停止。
- 现有采集、筛选、入库、暂停和取消测试保持通过。

### 11.3 API 和前端测试

- 平台状态接口只允许管理员访问。
- 平台状态返回运行、排队和登录字段。
- 运行详情按平台和运行 ID 请求日志。
- 管理页面同时显示抖音和小红书状态。
- 前端 lint 和生产构建通过，界面无新增英文可见文本。

## 12. 验收标准

- 抖音和小红书任务可以同时处于 `running`。
- 同一平台提交两个任务时只有一个运行，另一个排队。
- 一个平台完成、失败或取消不会修改另一个平台的运行状态。
- 抖音采集期间可以启动小红书登录，反向同样成立。
- 运行详情只显示所属平台和所属运行的日志。
- 管理页面可同时看到两个平台各自的状态。
- 新增一个测试平台定义后，工厂可创建运行时并显示平台能力，无需修改调度、取消和队列代码。
- 不新增数据库迁移。
- 完整 Python 测试通过，前端 lint 和生产构建通过。

## 13. 回滚

- 数据库结构未变化，回滚不涉及数据迁移。
- 回退代码后恢复单 Worker 行为；运行表中的排队记录继续由旧 Worker 按创建时间领取。
- 若发布时已有两个平台同时运行，先停止服务再回滚，避免旧代码同时接管两个平台运行。

## 14. 风险与限制

| 风险 | 应对 |
|---|---|
| 两个浏览器进程增加内存占用 | 平台并发上限固定为每个平台一个，默认最多两个采集进程 |
| 日志查询仍可能取到同平台后续运行 | 日志条目记录 `run_id`，运行详情必须按两者过滤 |
| 全局调度器仍是单点 | 当前单实例部署可接受；多实例属于后续高可用范围 |
| 新平台被误认为只加配置即可 | 文档明确仍需任务枚举、账号能力和采集器适配 |
| 平台 Worker 写入竞争 | 保持短事务、幂等 upsert 和唯一约束 |
