# 邀请码注册与用户数据隔离设计

- 日期：2026-11-12
- 状态：已确认，待制定实施计划
- 范围：注册、登录身份、用户数据隔离、用户与平台组合运行时、数据库迁移
- 当前注册上限：一个普通用户
- 注册方式：固定邀请码
- 管理员页面：本阶段不实施

## 1. 目标

在保留现有环境变量管理员的前提下，新增一个邀请码注册的普通用户，并确保管理员与普通用户之间，以及后续新增用户之间的数据、运行进程、登录状态和浏览器资料相互隔离。

本阶段只开放一个普通用户。管理员和该普通用户是两个独立的数据所有者，所有隔离规则同时适用于两者。数据模型和运行时边界仍按多用户设计，避免后续开放更多用户时重写任务、运行和采集链路。

## 2. 已确认约束

- 注册邀请码固定配置在 `.env`，不在页面中管理。
- 邀请码缺失或为空时关闭注册。
- 当前只允许一个普通用户注册，并发请求也只能成功一次。
- 保留现有 `.env` 管理员登录。
- 管理员和普通用户都是数据所有者，现有业务接口只能访问当前登录用户自己的数据。
- 本阶段不提供用户列表、封禁、删除、密码重置或管理员页面。
- 用户管理数据当前与采集数据使用同一个 PostgreSQL，后续可以迁移到独立数据库或服务器。
- 抖音和中红书继续按平台运行；运行时进一步细分为“用户 + 平台”。
- 前端所有新增可见文字使用中文。

## 3. 身份模型

### 3.1 用户类型

新增 `collector_users` 表，保存：

- `id`：36 字符 UUID，稳定用户标识。
- `username`：登录名，保留用户输入。
- `username_normalized`：去除首尾空白并执行 `casefold()` 后的唯一登录名。
- `password_hash`：仅普通用户使用；环境变量管理员可以为空。
- `role`：`admin` 或 `user`。
- `credential_type`：`environment` 或 `password`。
- `status`：本阶段固定为 `active`。
- `registered_at`：普通用户注册时间。
- `created_at`：记录创建时间。

固定历史管理员 ID 为：

```text
00000000-0000-0000-0000-000000000001
```

环境变量管理员使用该 ID，但登录名仍来自 `ADMIN_USERNAME`，密码仍来自 `ADMIN_PASSWORD`。管理员密码不写入数据库。数据库中的管理员行使用固定内部用户名 `__environment_admin__` 作为身份锚点，不用于对外登录或页面展示；这样管理员更改环境变量登录名时不需要迁移历史数据的所有者 ID。

注册用户名必须先去除首尾空白并使用与登录相同的方式规范化。规范化结果不得等于 `ADMIN_USERNAME` 的规范化结果，也不得使用 `__environment_admin__` 等保留内部身份名，避免注册账号被同名的环境变量管理员遮蔽。

### 3.2 单用户注册上限

普通用户限制由两层保证：

1. 注册事务检查是否已经存在 `role = "user"` 的用户。
2. PostgreSQL 部分唯一索引限制只能存在一个 `role = "user"` 的行。

并发提交发生唯一约束冲突时，接口返回中文冲突提示，不得产生两个普通用户。

该部分唯一索引是当前单用户阶段的发布门禁。后续允许更多普通用户时，必须通过迁移显式移除该限制，不能只修改应用层检查。

### 3.3 密码与登录

- 普通用户密码长度要求为 12 到 128 个字符。
- 密码使用标准库 `hashlib.scrypt` 加随机盐哈希。
- 哈希格式包含算法、参数、盐和摘要，不在日志或响应中输出。
- 登录名规范化后比较，展示名保留原始大小写。
- 环境变量管理员优先按原有环境变量凭据验证。
- 普通用户按数据库密码哈希验证。
- 错误密码和不存在用户使用相同的中文错误提示，避免枚举账号。

## 4. 注册流程

### 4.1 配置

`.env` 新增：

```text
REGISTRATION_INVITE_CODE=至少16位的随机邀请码
```

规则：

- 未配置时，注册接口返回“注册当前未开放”。
- 配置后必须至少 16 个字符，应用启动时校验。
- 邀请码只参与服务端常量时间比较，不写入日志、响应、数据库或测试快照。

### 4.2 API

新增：

- `GET /api/auth/registration-status`：返回 `enabled` 和 `available`，不返回用户信息或邀请码。
- `POST /api/auth/register`：接收用户名、密码和邀请码。
- `GET /api/auth/me`：增加用户 ID 和角色，同时保留用户名。

注册请求必须带现有 CSRF Cookie 和 `X-CSRF-Token`。注册尝试按客户端 IP 限流，邀请码错误、名额已使用和请求过于频繁均返回中文提示。

注册状态判断顺序固定为：注册未开放、邀请码错误、普通用户名额已使用、用户名冲突。注册名额检查和用户创建在同一事务内完成；即使状态查询时显示仍可注册，最终并发结果也必须以数据库唯一约束为准。

注册成功后：

1. 创建普通用户。
2. 创建绑定该用户 ID 的登录会话。
3. 设置登录 Cookie 和 CSRF Cookie。
4. 返回当前用户基本信息。

前端注册成功后直接进入工作台。

## 5. 会话与认证依赖

现有 `collector_admin_sessions` 改为 `collector_sessions`：

- 保留令牌摘要、CSRF 摘要、创建时间、过期时间和撤销时间。
- 增加非空 `user_id`。
- 会话查询联查有效用户和 `status = "active"`。
- 旧单管理员会话在升级时删除，用户需要重新登录。

认证依赖返回结构化的当前用户：

```text
AuthenticatedUser(id, username, role)
```

业务接口必须使用当前用户的 `id` 作为数据所有者。禁止继续通过固定环境变量用户名推断数据归属。

现有 `require_admin` 名称可以在兼容层保留，但业务权限不再表示“查看所有数据”，而是表示“已登录且处于有效状态”。新代码优先使用语义明确的 `require_user`。

## 6. 数据模型与隔离规则

### 6.1 归属字段

下列表增加非空 `owner_id`，当前数据库中外键指向 `collector_users.id`：

- `collector_filter_rules`
- `collector_tasks`
- `collector_runs`
- `collector_comments`
- `collector_comment_snapshots`

即使运行可以通过任务关联推断用户，运行仍直接保存 `owner_id`，方便调度、取消和日志校验，避免每次都依赖多表关联。

该外键只适用于“用户表与业务表当前同库”的部署阶段。未来拆分独立用户数据库时，必须先移除跨库外键，但仍保留稳定的 `owner_id` 值和所有应用层过滤条件。

### 6.2 唯一约束

- 用户登录名规范化后全局唯一。
- 筛选规则版本按 `owner_id + lineage_id + version` 唯一。
- 评论按 `owner_id + platform + external_comment_id` 唯一，不同用户可以保存同一平台评论。
- 评论快照按 `owner_id + comment_id + run_id` 唯一。

### 6.3 查询规则

- 列表查询首先增加 `owner_id = current_user.id`。
- 单条查询使用 `id + owner_id` 联合条件，或先加载后比较所有者。
- 访问其他用户存在的记录时返回“不存在”，不返回“无权限”，避免泄露记录存在性。
- 任务关联筛选规则时，规则的 `owner_id` 必须与任务所有者一致。
- 运行只能从当前用户的任务创建。
- 评论快照必须属于当前用户的评论和运行。
- 导出评论、评论详情和快照历史都必须带用户过滤。
- WebSocket 日志和状态流只发送当前用户的数据。

### 6.4 现有数据迁移

迁移完成后：

- 现有筛选规则、任务、运行、评论和快照全部归到固定历史管理员 ID。
- 环境变量管理员登录后仍可查看现有数据。
- 普通用户首次登录时看到空任务、空运行、空评论和空筛选规则。

## 7. 后台调度与平台运行时

### 7.1 运行时注册键

平台运行时从“平台”改为“用户 ID 与平台”的组合：

```text
PlatformRuntime(owner_id, platform)
```

每个运行时拥有独立的：

- `CrawlerManager`
- `PlatformCollectionWorker`
- 当前运行 ID
- 进程状态
- 日志缓冲和日志队列
- 平台登录状态
- 浏览器资料目录

当前阶段虽然只有一个普通用户，但管理员和普通用户仍分别拥有各自的“用户与平台”运行时。例如管理员抖音、管理员小红书、普通用户抖音和普通用户小红书分别使用四个独立运行时。未来增加普通用户时沿用同一注册键，不改变任务、运行和日志结构。

### 7.2 调度与领取

- 全局调度器仍创建一个到期运行，但运行必须带 `owner_id`。
- 每个用户与平台组合对应一个 Runner。
- Runner 领取任务时同时匹配 `owner_id`、`platform` 和 `queued` 状态。
- 同一用户同一平台串行；不同用户或不同平台可以独立运行。
- 启动、停止、取消和日志查询必须先解析当前用户，再选择对应运行时。
- 注册新用户后，监督器按需创建该用户的平台运行时。

### 7.3 平台状态

`GET /api/platforms/status` 继续返回抖音和小红书两个条目，但只统计当前用户：

- 当前用户排队运行数
- 当前用户当前运行 ID 和任务 ID
- 当前用户进程状态
- 当前用户平台登录状态

管理员和普通用户不共享平台状态卡片。

## 8. 平台账号与浏览器资料

账号服务全部增加用户 ID 参数：

- `account_status(user_id)`
- `start_login(user_id, platform)`
- `unbind(user_id, platform)`
- `login_active(user_id, platform)`
- `profile_dir(user_id, platform)`
- `login_marker_path(user_id, platform)`

目录规则：

- 历史管理员继续使用原有 `browser_data/*_user_data_dir` 和 `.login_state`，避免现有登录失效。
- 普通用户使用 `browser_data/users/<owner_id>/<platform>_user_data_dir`。
- 普通用户登录标记使用 `browser_data/users/<owner_id>/.login_state/<platform>.json`。
- 解绑路径必须验证在目标用户目录内，禁止删除其他用户或浏览器资料根目录。

采集子进程通过环境变量接收当前用户目录：

- `COLLECTOR_USER_ID`
- `COLLECTOR_USER_DATA_DIR`
- `COLLECTOR_LOGIN_STATE_DIR`

上游平台代码和登录标记写入代码读取这些环境变量。不得通过修改全局 `config.USER_DATA_DIR` 在并发运行时之间切换目录。

## 9. 日志与 WebSocket

- 日志条目增加 `owner_id`。
- `/api/crawler/logs` 同时校验 `owner_id`、可选 `platform` 和可选 `run_id`。
- 无过滤条件时只合并当前用户各平台的日志。
- 运行详情只能获取当前用户运行 ID 的日志。
- WebSocket 日志连接建立时解析当前用户，只推送该用户日志。
- WebSocket 状态流只包含当前用户的平台运行时。
- 登录流程产生的日志同样带用户归属，运行详情仍可只显示与具体运行 ID 匹配的日志。

## 10. 前端

### 10.1 登录页

- 从“单管理员登录”改为“账号登录”。
- 增加“注册账号”切换入口。
- 注册表单包含用户名、密码、确认密码和邀请码。
- 注册成功后直接进入工作台。
- 注册名额使用后入口显示“注册名额已使用”。
- 邀请码缺失时入口显示“注册当前未开放”。

两个提示同时成立时优先显示“注册当前未开放”，与后端注册状态判断顺序一致。

### 10.2 工作台

- 现有任务、运行、评论、筛选规则、账号和平台状态接口自动按当前用户返回数据。
- 页面不增加用户切换控件。
- 顶部显示当前登录用户名。
- 退出登录行为保持不变。
- 所有新增错误、状态和提示使用中文。

## 11. API 错误语义

统一增加中文安全提示：

- 注册未开放
- 邀请码错误
- 当前仅允许注册一个用户
- 用户名已存在
- 用户名或密码错误
- 用户账号不可用
- 注册尝试次数过多

对外不返回密码哈希、邀请码、内部 SQL 错误或其他用户记录 ID。

## 12. 数据库迁移

新增单个 Alembic 迁移：

1. 创建 `collector_users` 表和历史管理员记录。
2. 创建单普通用户部分唯一索引。
3. 将旧 `collector_admin_sessions` 重命名为 `collector_sessions`，删除旧会话并增加 `user_id`。
4. 为筛选规则、任务、运行、评论和快照增加带默认历史管理员 ID 的 `owner_id`。
5. 更新旧唯一约束、外键和索引。
6. 增加用户维度的查询索引。
7. 验证所有旧数据均可回填，再移除临时默认值。

降级迁移必须恢复旧唯一约束并删除用户归属字段。由于旧会话已主动失效，降级后用户需要重新使用环境变量管理员登录。

## 13. 安全要求

- 邀请码使用常量时间比较。
- 密码哈希必须带随机盐，不使用明文、普通 SHA-256 或可逆加密。
- 注册与登录按 IP 限流，不记录用户名、密码或邀请码。
- Cookie 保持 `HttpOnly`、`SameSite=Lax`，云端继续支持 `Secure`。
- 所有写接口继续要求 CSRF。
- 所有用户数据查询使用服务器解析的用户 ID，不接受客户端提交 `owner_id`。
- 任务、运行、规则、评论、日志和账号接口均覆盖横向越权测试。
- 浏览器目录操作进行安全路径校验。
- 本阶段不声称已经具备 PostgreSQL 行级安全策略；应用层隔离和双用户回归测试是当前发布门禁。

## 14. 测试与验收

### 14.1 单元与集成

- 邀请码缺失关闭注册，错误邀请码拒绝注册。
- 注册用户名不得与环境变量管理员或保留内部身份名冲突。
- 第一个普通用户注册成功，第二个用户返回冲突。
- 并发注册只能创建一个普通用户。
- 密码哈希可验证且不等于明文。
- 环境变量管理员仍可登录。
- 普通用户可以登录、获取 `/me` 和退出。
- 普通用户与管理员看到的任务、运行、评论、规则和平台状态互不混合。
- 用户 A 无法读取、修改、运行、取消、导出或查看用户 B 的记录。
- 用户 A 无法使用用户 B 的浏览器资料登录或解绑。
- 调度器只由所属用户运行时领取运行。
- WebSocket 日志与状态不跨用户发送。
- 现有数据迁移后归历史管理员，普通用户初始数据为空。

### 14.2 前端

- 登录和注册页面在桌面与移动尺寸下可用。
- 注册名额使用后表单状态正确。
- 所有新增可见文字为中文。
- 前端 lint 和生产构建通过。

### 14.3 真实环境

- 使用隔离测试数据库执行完整迁移。
- 使用管理员和一个普通测试账号验证双用户隔离。
- 真实抖音和小红书采集仅使用测试用户自己的账号目录，小范围验证后停止。
- 不把真实账号 Cookie、密码或邀请码写入测试记录。

## 15. 非目标

- 管理员用户管理页面。
- 多个普通用户注册。
- 邮箱验证、短信验证或找回密码。
- 用户删除、禁用和角色管理。
- 邀请码创建、过期或使用次数管理。
- PostgreSQL 行级安全策略。
- 用户数据库真正部署到另一台服务器。
- 多实例调度器和分布式锁。

## 16. 后续演进

当管理员页面和独立用户数据库实施时：

1. 将 `collector_users` 和会话迁移到用户管理数据库。
2. 业务数据库只保留稳定 `owner_id`，不使用跨数据库外键。
3. 通过认证服务或本地用户缓存解析当前用户。
4. 增加管理员查看、禁用和配额管理功能。
5. 如需要更强隔离，再评估 PostgreSQL RLS 或按用户分库。

当前实现不得假设用户数据库永远位于同一 PostgreSQL。
